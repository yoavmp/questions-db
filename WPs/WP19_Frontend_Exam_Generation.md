# WP19 — Connect the exam-generation frontend

## Goal

Connect the existing React/Vite exam screen to the persistent backend job API implemented in WP18/WP18R. Preserve the existing DOCX workflow and make mixed DB/LLM generation usable end to end.

## Required work

### 1. Backend hardening

- Give `replace_from_db` the same concurrency protection as other job mutations. A double click or concurrent request must not cause a lost update, duplicate selection, or corrupt persistence.
- Expose useful attempt/retry telemetry from the immutable cost ledger, by category and slot, so charged failed attempts remain diagnosable after rollback.
- Keep the initially requested `C/A/B` values as request provenance only. **Do not compute, enforce, or display a current DB/LLM balance after replacements.** Replacements may change that balance freely.

### 2. Category inputs

- Render all 20 categories in the canonical order returned by `/api/test/categories`.
- Show three nonnegative-integer inputs per category, in this order:
  1. total desired questions (`C`)
  2. questions from DB (`A`)
  3. questions generated by LLM (`B`)
- Editing `C` sets `A = ceil(C/2)` and `B = floor(C/2)`.
- Editing `A` or `B` sets `C = A + B`.
- If `A` exceeds DB availability, show an inline error and block start; do not silently clamp it.
- Provide an editable whole-exam cost ceiling, default `$5.00`.
- Show stale-pricing warnings. Missing, mismatched, or incomplete pricing blocks only requests with `B > 0`; DB-only generation must remain usable.

### 3. Start, persistence, and progress

- Create jobs through `POST /api/exam-jobs`; prevent double submission.
- Preserve the active job ID across refresh/reopen (local storage and, if compatible with the current router, the URL).
- Resume by polling `GET /api/exam-jobs/<job_id>`.
- Show overall, per-category, and per-slot progress. Display accepted partial results immediately.
- Handle `completed`, `partial`, `interrupted`, `cost_ceiling`, and `failed` states clearly.
- Allow retry of eligible slots. Allow raising the ceiling through the existing `PUT` endpoint and then retrying.
- Permit only one mutation per slot at a time. Disable relevant controls and show progress during a request. On failure, keep the current question visible and unchanged.

### 4. Results and replacements

- Present questions in canonical category/global-number order.
- Mark every current question clearly as either DB or LLM generated. These per-question origin badges are the only post-generation composition indicator required.
- Show both controls on **every accepted question**, regardless of current origin:
  - `החלף בשאלה מהמאגר`
  - `צור שאלה אחרת`
- Connect them to the two WP18R replacement endpoints and refresh the view from the server response.
- Verify all transitions: DB→DB, DB→LLM, LLM→DB, LLM→LLM. The badge must update to the new origin.
- Do not retain displaced DB questions for semantic uniqueness. Retain displaced LLM questions according to the implemented history policy.
- Show cumulative LLM cost, accounting basis (`calculated`, `conservative`, or mixed), warnings, and retry/attempt telemetry. Do not invent precision absent from the backend.

### 5. Existing output workflows

- Keep one-click Hebrew DOCX generation working from the final current question set.
- Strip job-only metadata before passing questions to the existing DOCX path; preserve existing answer randomization.
- Provide the generated-question Excel download through the existing job export endpoint.
- Generated questions must never be inserted into the DB automatically.

### 6. UI migration and quality

- The new screen must use the asynchronous job API, not the legacy synchronous `/api/test/generate` flow.
- Remove the old single replacement control from this screen. Do not delete legacy backend endpoints merely because this screen no longer uses them.
- Keep the existing visual language, Hebrew RTL behavior, accessible labels, keyboard behavior, and responsive layout.

## Verification

Use fake API fixtures and block external network/provider calls. Add tests for:

- `C/A/B` arithmetic, integer validation, DB availability, canonical order, and readiness behavior;
- start protection, polling, refresh resume, progress/partial states, interruption, retry, and cap increase;
- both replacement buttons for both origins, all four origin transitions, failure rollback, and mutation locking;
- absence of any recomputed/current aggregate DB-vs-LLM count;
- ledger-derived attempt telemetry, cost warnings, Excel download, and DOCX metadata stripping.

If the frontend has no test framework, add the smallest justified Vitest/Testing Library setup. Run:

- full backend tests serially with an isolated temporary DB;
- frontend unit/component tests and production build;
- only targeted generator contract tests if integration imports require them (the submodule must not change).
